# Вопросы Cumsino: стандарты и выводы

Документ фиксирует, как устроена генерация вопросов после переработки (октябрь 2026, патч 7.41f):
откуда берутся данные, какие есть категории, по каким правилам пишутся вопросы и варианты,
и что мы выяснили по дороге. Что ещё предстоит — в [BACKLOG.md](BACKLOG.md).

Рабочий код — `scripts/` и `scripts/generate/numeric_lab/`. Игра пока читает **старые** файлы
`scripts/data/generated/*_main.json`; перенос нового банка в игру — в бэклоге.

---

## 1. Источник истины

### Снимок данных

`python scripts/fetch_dota_data.py` скачивает данные на зафиксированных коммитах и пишет
`scripts/data/dota/manifest.json` (патч, sha, контрольные суммы), печатает diff со старым снимком
и пересобирает индекс актуального контента.

| Источник | Куда | Что даёт |
|---|---|---|
| `odota/dotaconstants` | `scripts/data/dota/*.json` | разобранные значения и описания: heroes, hero_abilities, abilities, aghs_desc, items, patch, patchnotes |
| `dotabuff/d2vpkr` | `scripts/data/dota/game/` | сырые файлы игры: items.txt, neutral_items.txt, shops.txt, файлы героев, abilities_russian.txt |

Особенности dotaconstants, которые надо помнить:
- **не удаляет вырезанное**: старые предметы и способности остаются с замороженными полями;
- **не выгружает бонусы Aghanim's Scepter / Shard** (≈376 значений, существующих только с улучшением, и ≈276 прибавок) — берём их из сырых файлов героев;
- значения предметов по уровням бывают строкой `"400 / 500 / 600"` — разбирать как уровни;
- примечаний к способностям (серые строки тултипа) и русских текстов нет — они есть в `abilities_russian.txt` (≈1055 примечаний) и в `abilities_english.txt`; обе локализации лежат в снимке, английская — источник описаний, примечаний и текстов шарда/аганима для вопросов про механики.

### Что сейчас в игре — `scripts/data/dota/current.json`

Строит `scripts/build_game_index.py` (вызывается из fetch). Парсер формата игры — `scripts/valve_kv.py`.

Предметы по категориям:

| Категория | Как определяется | В вопросы |
|---|---|---|
| `shop` | есть в shops.txt | да |
| `upgrade` | улучшение по рецепту вне магазина (BoT 2) | да |
| `level` | уровень другого предмета (Dagon 2–5 → уровни Dagon) | значениями базового |
| `neutral` | текущие тиры neutral_items.txt | да |
| `enhancement` | чары из neutral_items.txt | да |
| `roshan` | дроп Рошана + Aghanim's Blessing | нет |
| `removed` | IsObsolete или нейтралка вне текущих тиров | нет |
| `other` | служебное и ивентовое | нет |

Способности — слоты из файла героя, роль из AbilityDefinitions: `basic`, `ultimate`, `innate`,
`shard`, `scepter` (в вопросы), `sub` (служебные кнопки Stop/Release/Toggle), `review` (решить
вручную). Ручные решения — `scripts/data/dota_overrides.json`, переживают обновление патча.

## 2. Категории вопросов

Категория — отдельный ключ выборки, отдельные запросы к модели и поле `category` у вопроса.

| Категория | Что | Тип | Состояние |
|---|---|---|---|
| `heroes` | способности, аганим и шард | числовой | готово: 491 вопрос (`out/full1`) |
| `items` | магазин и улучшения по рецепту | числовой | готово: 154 (`out/full1`) |
| `neutrals` | нейтралки | числовой | готово: 44 (`out/full1`) |
| `enhancements` | чары к нейтралкам | числовой | готово: 10 (`out/full1`) |
| `costs` | цены предметов | числовой | готово: 173, 9 исключено (`out/costs2`) |
| `talents` | «какой из этих талантов есть у героя» | текстовый | готово: 51 (`out/talents-full`) |
| `mechanics` | как работает, ложный факт, сработает или нет, чья механика | текстовый | готово: 116 после курирования (`text_lab/out/full1`) |
| внешние источники | популярность, винрейт героев и предметов | разный | в бэклоге |

Числовой вопрос работает в обоих режимах игры: в «ближе всех» игрок вводит число, в
«4 варианта» варианты строит игра по шагу (раздел 4).

## 3. Стандарт числового вопроса

### Модель выбирает факт, число берётся из данных

Модель получает факты (`fact_id`, подпись из игры, значения по уровням) и возвращает
`fact_id`, `level`, текст вопроса, единицу и `step`. **Правильный ответ модель не пишет**:
его подставляет код по `fact_id` и `level`. Значения модель видит — без них не выбрать
интересный факт и правдоподобный шаг. Поэтому ответ всегда совпадает с игрой, а при
обновлении патча обновляется сам.

Выход проверяется structured outputs: JSON-схема, `fact_id` ограничен фактами из запроса (enum).

### Что спрашиваем и что нет

Не спрашиваем (отсекается в данных или в промпте):
- расстояния: радиусы, дальности, ширину, скорость снарядов — неинтуитивно;
- мана-кост; цены — отдельная категория;
- скрытые служебные значения (`hidden`), если их не видно глазами в игре;
- «дефолтные» значения: **0, 1, 2, 50, 100, 1200 и 30%** и другие очевидно круглые.

Производные значения не запрещаем и не просим.

### Уровни

- Только **первый или максимальный** уровень — у способностей (включая ультимейты) и у предметов с уровнями.
- Максимальный называется словами («на максимальном уровне»); у ультимейта можно «на 3-м уровне».
- Если у сущности есть `level_names` или `call_as` — называть по ним. Это данные, а не правила промпта:
  - Dagon: «Dagon 1 … Dagon 5»;
  - нейтралки: «нейтралка 1-го тира Kobold Cup»;
  - чары: «чара на нейтралки 2-го тира Brawny» (уровень чары однозначно соответствует тиру).

### Язык и сленг

Текст по-русски, коротко и разговорно. Названия героев, способностей и предметов — по-английски,
как в клиенте. Термины — сленгом:

| Не пиши | Пиши |
|---|---|
| оглушение | стан |
| безмолвие | сайленс |
| обезоруживание | дизарм |
| обездвиживание | рут |
| превращение | хекс |
| разрушение пассивок | брейк |
| замедление | слоу |
| вампиризм | лайфстил |
| вампиризм от заклинаний | спелл-лайфстил |
| усиление заклинаний | спелл-амп |
| сопротивление эффектам | статус-резист |
| сопротивление магии | маг. резист |
| развеивание | диспел |
| невидимость | инвиз |
| истинное зрение | просвет |
| критический удар | крит |
| перезарядка | кд |

Без изменений: «невосприимчивость к магии», «уклонение», «скорость атаки», «скорость
передвижения», «кровотечение», «горение».

### Размер запроса и квоты

Каждая категория — отдельными запросами, порядок сущностей внутри категории случайный
(seed пишется в `run.json`). Квота подставляется в `{QUOTA}` общего промпта `prompt_v7.md`
(`CATEGORY_SETUP` в `run_api.py`).

| Категория | Сущностей в запросе | Квота |
|---|---|---|
| heroes | 3 | 2–4 вопроса на героя, из разных способностей |
| items | 10 | обычно 1 на предмет, для особенно интересного 2; слабые пропускать |
| neutrals | 10 | как предметы |
| enhancements | все одним запросом | ~0.5 на чару, не больше одного |
| costs | все одним запросом | все, кроме ~5% самых очевидных, с причиной |
| talents | 10 героев | ~4 вопроса на запрос, не больше одного на героя |

### Модель и вызовы

- `claude-opus-5-5`, `effort: high`.
- Обычные параллельные вызовы (`--sync`), **без Batch API**.
- **Без `cache_control`**: схема с enum по `fact_id` уникальна для запроса и попадает в кэшируемый префикс, поэтому кэш никогда не читается и только стоит +25% за запись.
- Ключ — переменная окружения `NUMLAB_API_KEY`: имя `ANTHROPIC_API_KEY` в облачном окружении занято платформой.

## 4. Стандарт вариантов ответа: шаг

Модель для каждого вопроса задаёт только `step` — насколько ошибается игрок, который помнит
значение примерно. Варианты строит **игра при каждом показе вопроса**:

1. Случайно выбирается позиция правильного ответа среди четырёх вариантов по величине (крайняя
   или одна из центральных, равновероятно), кроме позиций, при которых варианты ушли бы в ноль
   и ниже.
2. Остальные варианты откладываются от правильного ответа ровно на заданный шаг:
   `answer + (i − p) · step`, с точностью шага и ответа.
3. Порядок показа перемешивается отдельно.

Позиция ответа случайна по построению: ни расположение, ни шаг не выдают правильный вариант.
Эталон — `scripts/generate/numeric_lab/options.py`; в отчётах лаборатории вариантов нет, только шаг.

Режим «ближе всех» вариантов не использует: только ответ.

## 5. Стандарт вопросов про таланты

- Код размечает таланты: `stat` — голый стат без способности (149), `tweak` — правка числа у способности (779), `mechanic` — меняет поведение (93).
- Вопрос только один: «Какой из этих талантов есть у героя?» — 1 настоящий + 3 выдуманных.
- Настоящий — почти всегда `mechanic`; `tweak` — только если число наглядное (лишний фамильяр, заряд, цель). Голые статы и правки чисел — зубрёжка, не берём.
- Подделки модель выдумывает как механики этого героя, с опорой на описание способности, без чисел; одна и та же формула («пробивает невосприимчивость», «даёт брейк») — не больше раза на ответ.
- Варианты по-русски со сленгом; настоящий талант — точный перевод (оригинал хранится рядом).
- Проверка:
  1. код — состав 1 + 3, настоящий вариант действительно талант героя;
  2. второй проход модели (`prompt_talents_verify.md`) — для каждого варианта `real_talent` / `not_a_talent` / `already_default` (способность и так это делает) / `too_close`, плюс точность перевода.

## 5a. Стандарт вопросов про механики

`scripts/generate/text_lab/` — вопросы без чисел про поведение способностей.

- **Вход** (`mechanics_lab.py`) — по каждой способности героя: роль, поведение, тип урона,
  `bkbpierce`, `dispellable`, полное описание из `abilities_english.txt`, примечания
  (`Note0…`) и тексты шарда/аганима; метки `%value%` заменены числами из файлов героя.
- **Запрос** — 5 героев, ~1 вопрос на героя (4–6 на запрос). Модель Opus, effort high —
  как у остальных категорий; качество подделок решают промпт и примеры, xhigh не понадобился.
- **Форматы:** `how` (как работает), `false_fact` (три правды и ложь), `interaction`
  (что сбивает / пробивает / работает на иллюзиях…), `whose` (механика без названия).
- **Подделки — главное.** Объект вопроса и верный ответ модель выбирает хорошо, портят
  вопрос неверные варианты. Правила (`prompt_mechanics_v4.md`) выведены из ручных вопросов
  пользователя, 9 из них стоят в промпте примерами:
  1. подделка собрана из настоящего материала — соседняя способность, реальное условие
     с чужого героя, настоящее свойство не на своём месте;
  2. отличается от истины одной деталью («откатывает урон» ↔ «восстанавливает прежнее хп»);
  3. меню из комбинаций составляющих (дальше / дальше + стан / дальше + урон / всё);
  4. наивный ответ как ловушка («Всегда»);
  5. радикальный верный ответ («Никак», «Ничего»);
  6. в ложном факте правды контринтуитивны, а ложь звучит нормально и сделана из
     настоящей механики той же способности;
  7. одинаковая форма вариантов;
  8. у каждой подделки своя причина казаться верной; без выдумок, отметаемых с первого
     прочтения, и без зубрёжки списков исключений;
  9. избитые шаблоны (брейк и накопительный пассив, Linken и ненаправленный каст, BKB после
     каста) — только если ответ отличается от привычного правила.
- **Доказательство:** у каждого варианта `evidence` — способность и место в данных
  (`desc`, `noteN`, `shard`, `scepter`, `bkbpierce`, `dispellable`) или `invented`; верный
  вариант всегда опирается на данные.
- **Проверка:**
  1. код — 4 варианта, ровно один верный, ссылки существуют, верный не выдуман, комментарий
     не пустой и без обрывков JSON;
  2. второй проход модели (`prompt_mechanics_verify.md`) — истинность каждого утверждения
     (`true` / `false` / `unknown`);
  3. ручное курирование (`curate.py` + `curation.json` в папке прогона) → `bank.json`.
- `comment` — одна фраза, которую игроки видят после раскрытия ответа.

## 6. Стандарт цен

Один запрос на все предметы магазина (`prompt_costs_v2.md`): вопрос про каждый, кроме ~5%
самых очевидных (Tango, Iron Branch, Boots of Speed, TP, Sentry, Salve, Clarity, Smoke,
Quelling Blade), причина исключения записывается. Шаг кратен 25/50/100/200/250 и подбирается
под предмет: Blood Grenade — 10, Hand of Midas — 100, Boots of Travel — 250.

## 7. Проверки (`resolve.py`)

Отчёт по прогону — `report.md` в папке прогона. Флаги:
- значение зависит от уровня, а уровень не указан (имена уровней из `level_names` засчитываются);
- уровень не первый и не максимальный; максимальный назван числом (кроме ульт и предметов);
- скрытое значение;
- числа из данных в тексте вопроса (возможная подсказка);
- шаг ≤ 0, шаг ≥ ответа, шаг меньше 3% от ответа (для цен порог, вероятно, надо снизить);
- вопрос сверх квоты категории.

## 8. Что мы выяснили

**Про модели**
- Модель не держит равномерную позицию правильного ответа, когда вопросов в ответе мало: 0/7/7/0 в одиночных запросах, 2/2/8/2 на 14 вопросах. На 173 вопросах в одном ответе — почти идеально (43/44/44/42). Отсюда шаг и генерация вариантов кодом.
- Свои неверные варианты модели строят с одинаковым шагом (41 из 92) и подставляют значения других уровней — это выдаёт ответ.
- Повторный прогон того же промпта даёт почти те же факты (13 из 14). Состав группы меняет выбор: в смешанных группах другой факт у 7 из 13 сущностей.
- Opus против Sonnet: Opus лучше держит инструкции и неверные варианты; по выбору фактов разница небольшая. Цена не аргумент: полный числовой прогон стоит единицы долларов.
- Модель правильно пишет число, но может ошибиться в тексте: Opus описал у Culling Blade порог добивания из старых патчей. Привязка к `fact_id` защищает число, не формулировку.
- В талантах модель выдумывает подделки шаблонно: удваивает число (−15s → −25s, +1 → +2), повторяет «пробивает невосприимчивость» — нужны явные запреты в промпте.
- В механиках модель хорошо выбирает объект и верный ответ, но без примеров делает подделки, которые отметаются сразу («ремнант катится вместе с героем», «Grip не притянет союзника под сайленсом») или просто отрицают ответ. С правилами и ручными примерами (v2+) появились меню комбинаций, наивные ловушки и радикальные ответы; нелепых выдумок почти не осталось.
- Каждый запрос видит только своих 5 героев, поэтому по всему банку повторяются шаблоны: в полном прогоне 9 вопросов про брейк (почти везде «новые стаки не копятся, старые работают») и 4 про Linken (везде «не сработает»). Это лечится запретом в промпте (v4) и курированием, а не внутри запроса.
- Второй проход проверки моделью почти ничего не ловит (2 флага `unknown` из 127). Выборочная сверка с примечаниями подтвердила даже странные ответы (Mystic Flare уничтожает иллюзии, Meat Hook проходит сквозь здания), но проверка смотрит на соответствие данным, а не на качество подделок — его оценивает только человек.
- «Вижн» неоднозначен: перевод «True Sight» как «даёт вижн» потерял смысл (Rocket Flare и так даёт обзор). Истинное зрение теперь — «просвет».

**Про API**
- Batch API на практике: 37+ минут в очереди без единого обработанного запроса, а синхронно те же 38 запросов прошли за 31 с. Для наших объёмов не нужен.
- Кэш не работает с уникальной схемой на запрос (см. раздел 3).
- `temperature` API больше не принимает: разнообразие идёт от входа и промпта.

**Про старый пайплайн** (`scripts/generate/gen_questions.py`, `improve_questions.py`)
- брал способности по префиксу имени героя — в генерацию попадали 157 вырезанных способностей (Combustion, Quick Wit, Cutpurse…);
- фильтр предметов `cost > 0` пропускал 15 вырезанных и терял все текущие нейтралки, Dagon 2–5 и Observer Ward;
- обрезал описания и параметры, не помечал скрытые значения;
- число писала модель — отсюда выдуманные значения, которые нечем проверить;
- `improve_questions.py` склеивал ответы через `zip` по порядку: пропуск одного вопроса сдвигал варианты на чужие вопросы;
- в игровые варианты попали пометки ручной чистки («Че за бред ваще», «бляя, что он написал»).
